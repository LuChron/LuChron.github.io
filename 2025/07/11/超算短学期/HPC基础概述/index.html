# Openmp

Openmp is an API that supports muti-platform shared-memory multiprocessing programming in C C++ Fortran

#pragma omp parallel{                   
	printf("to do sth");
}

代码中间小的任务叫做 section

#include <stdio.h>
#include <omp.h>

int main() {
    printf("Welcome to OpenMP!\n");
    
    #pragma omp parallel
    {
        int ID = omp_get_thread_num();
        printf("hello(%d) ", ID);
        printf("world(%d)\n", ID);
    }          //这里面是并行运算程序
    
    printf("Bye!");
    return 0;
}

# 1 调度策略

这张图对比了 OpenMP 中 for 循环的三种主要调度策略：static, dynamic, 和 guided。它们决定了循环的迭代任务如何被分配给不同的线程。

# (1) schedule(static) - 静态调度

  • 工作原理: 在循环开始之前，将所有迭代任务（循环的每一次）平均分成大块，然后静态地、永久地分配给每个线程。例如，如果有100个任务和4个线程，线程0得到任务1-25，线程1得到26-50，以此类推。这是一种简单、低开销的分配方式。
  • 图中表现:
  • 你可以看到每个线程都分到了一大段连续的任务。
  • 性能极差 (约 3.6s)。因为负载不均衡，线程3不幸地分到了一堆耗时长的黄色任务，而其他线程（特别是线程2）很快就完成了它们的短任务，然后就进入了长时间的等待。这造成了严重的负载不均衡和资源浪费。
  • 适用场景: 当每次循环迭代的计算量都完全相同时（负载均衡），静态调度是最高效的，因为它几乎没有管理开销。

# (2) schedule(dynamic, 1) - 动态调度

  • 工作原理: 任务不是预先分配的。它会维护一个任务池。每当一个线程完成当前任务后，它就会动态地去任务池里请求下一个任务来做。1 表示每次只请求一个任务（chunk size = 1）。
  • 图中表现:
  • 任务的分配是交错的。黄色和绿色的任务块被分散在所有线程中。
  • 性能最好 (约 2.25s)。当一个线程完成一个短的绿色任务后，它能立刻去领一个新的任务（可能是黄色或绿色），而不会闲置。这确保了所有线程都持续有活干，直到所有任务被完成。最终，所有线程几乎在同一时间结束工作。这就是良好的负载均衡。
  • 适用场景: 当每次循环迭代的计算量非常不确定或严重不均衡时，动态调度是最佳选择。它的缺点是管理开销比静态调度高，因为线程需要频繁地请求任务。

# (3) schedule(guided, 1) - 导向式调度

  • 工作原理: 这是 static 和 dynamic 的一种折中方案。它开始时分配较大的任务块（为了降低管理开销），随着任务池中剩余任务的减少，分配的任务块也越来越小（为了在最后阶段实现更好的负载均衡）。1 表示最小的任务块大小为1。
  • 图中表现:
  • 你可以看到，在开始阶段，分配的任务块较大；越往后，任务块变得越零碎。
  • 在此例中性能不佳 (约 3.6s)。不幸的是，在初始的大块分配中，线程3还是分到了耗时长的任务组合。虽然最后阶段任务分配变细了，但已经无法弥补早期分配不均造成的巨大时间差。
  • 适用场景: 适用于负载不均衡，但又想避免 dynamic 调度可能带来的较高管理开销的情况。它通常是一个不错的通用选择。

# 2 同步指令

OpenMP 中两个至关重要的同步指令：critical 和 atomic。

这两个指令的根本目的都是为了解决同一个问题：竞争条件 (Race Condition)。

# 1. 什么是竞争条件？

当多个线程同时尝试读取和修改同一个共享内存地址时，由于操作系统对线程的调度顺序是不可预测的，最终的计算结果会取决于哪个线程“跑得快”，导致结果出现错误或不确定。这就是竞争条件。

一个最经典的例子是并行累加：

int total_sum = 0;
#pragma omp parallel for
for (int i = 0; i < 1000; i++) {
   // 危险操作！
   total_sum = total_sum + 1; 
}
// 最终 total_sum 的结果很可能小于 1000

为什么会出错？因为 total_sum = total_sum + 1 并不是一个单一的操作。它在底层至少分为三步：

  1. 读取 total_sum 的当前值到线程的寄存器。
  2. 在寄存器中计算 +1。
  3. 将寄存器中的新值写回到 total_sum。

想象一下两个线程同时执行这个操作：

时间 线程 A 操作 线程 B 操作 total_sum 的值
T1 读取 total_sum (值为 50) 50
T2 读取 total_sum (值为 50) 50
T3 计算 50 + 1 = 51 50
T4 写回 51 到 total_sum 51
T5 计算 50 + 1 = 51 51
T6 写回 51 到 total_sum 51

两个线程都执行了加法，但 total_sum 只增加了1次。这就是竞争条件。为了解决这个问题，我们需要确保这个“读-改-写”的过程是互斥 (Mutually Exclusive) 的，即同一时间只允许一个线程执行。critical 和 atomic 就是实现互斥的两种方法。

# 2. #pragma omp critical

critical 指令定义了一个代码块 (Code Block)，这个代码块被称为临界区 (Critical Section)。它保证在任何时候，最多只有一个线程可以进入这个代码块执行。

可以把它想象成一个带锁的房间。

  • 一个线程来到门口，如果房间是空的，它就进去并把门锁上。
  • 其他线程来到门口，发现门锁着，就必须在外面排队等待。
  • 直到里面的线程办完事出来，把锁打开，等待的线程中才会有一个被允许进去。

语法和示例：

int total_sum = 0;
#pragma omp parallel for
for (int i = 0; i < 1000; i++) {
   // 只有一个线程能进入这个花括号区域
   #pragma omp critical
   {
       total_sum = total_sum + 1;
       // 可以在这里做其他复杂的操作，比如打印
       // printf("Thread %d is updating sum\n", omp_get_thread_num());
   }
}
  • 优点:
  • 灵活强大: 可以保护任意长度和复杂度的代码块，包括函数调用、I/O操作（如 printf）等。
  • 缺点:
  • 开销较大: 实现 critical 通常需要操作系统级别的锁（如互斥锁 Mutex），这涉及到上下文切换，开销相对较高。如果临界区被频繁访问，会成为严重的性能瓶瓶颈，这种现象称为序列化 (Serialization)，即并行代码退化成了串行执行。

命名临界区 (Named Critical Section):
你还可以给临界区命名，#pragma omp critical (name)。只有同名的临界区才会互斥。这允许多个不相关的临界区可以并行执行。

#pragma omp critical (update_x)
{ x++; }

#pragma omp critical (update_y)
{ y++; }
// 这两个临界区不会互相阻塞

# 3. #pragma omp atomic

atomic 指令提供了一种更轻量级的方式来保护内存操作。它不保护代码块，只保护紧随其后的那一条特定类型的语句。

可以把它想象成一个原子操作 (Atomic Operation)，一个不可分割、不会被中断的操作。

  • 当一个线程执行 atomic 操作时，CPU 保证这个操作（比如“读-改-写”）会一次性完成，期间不允许任何其他线程插入。

语法和示例：

int total_sum = 0;
#pragma omp parallel for
for (int i = 0; i < 1000; i++) {
   // 只保护下面这一句特定的内存更新语句
   #pragma omp atomic
   total_sum = total_sum + 1; // 或者 total_sum++;
}
  • 优点:
  • 开销极低: atomic 通常能被编译器直接翻译成特殊的、高效的硬件指令（如 x86 架构下的 LOCK 前缀指令）。它避免了操作系统锁的开销，性能远高于 critical。
  • 缺点:
  • 限制严格: 它只能用于非常特定的、简单的内存更新语句，通常是形如 x = x op expr 或 x++, ++x 等形式。
  • 不能保护一个代码块，也不能保护函数调用或 I/O 操作。

# 4. critical vs. atomic 对比总结

特性 #pragma omp critical #pragma omp atomic
保护对象 一个代码块 { ... } 单条特定的内存更新语句
灵活性 高。可以保护复杂的逻辑、函数调用、I/O等。 低。只能用于 x++, x+=y 等简单表达式。
性能开销 较高。通常使用软件锁，可能引起线程阻塞和上下文切换。 极低。通常使用硬件原子指令，非常高效。
使用场景 保护复杂数据结构更新、文件写入、或者必须一起执行的多条语句。 简单的计数器、累加器、标志位设置等。
类比 带锁的房间（通用，但进出慢） 不可分割的魔法指令（特定，但瞬时完成）

# 何时使用哪个？

一个非常简单实用的准则：

如果能用 atomic，就一定要用 atomic。

只有当你要保护的操作无法被 atomic 覆盖时（比如要更新一个链表，或者要在一个事务里同时更新两个变量），你才应该考虑使用 critical。在大多数累加、计数的场景下，atomic 都是性能更优的正确选择。

# 3.1 什么是 MPI 和 MPI_Send？

  • MPI (Message Passing Interface): 是一种用于分布式内存并行编程的标准化接口。与 OpenMP（用于共享内存）不同，MPI 的模型是多个独立的进程 (Process)，每个进程都有自己独立的内存空间。它们之间不能直接访问对方的变量，必须通过发送和接收消息 (Messages) 来进行通信和数据交换。

  • MPI_Send: 这是实现点对点 (Point-to-Point) 通信的发送函数。一个进程调用它，将一块数据打包成消息，发送给指定的另一个进程。

可以把这个过程想象成寄快递：

  • 你要寄送一个包裹（数据）。
  • 你需要把包裹打包好，写上收件人地址、发件人信息等（填写 MPI_Send 的参数）。
  • 然后把包裹交给快递员（调用 MPI_Send 函数）。

# 3.2 函数参数详解

# 消息内容 (The "What")

  1. const void* buffer: 要发送的数据

    • 这是指向你要发送的数据的内存地址（指针）。比如，一个整数变量的地址、一个数组的起始地址等。
    • void* 表示它可以是任何类型的数据，非常灵活。

  2. int count: 发送元素的数量

    • 指明你要发送多少个元素，而不是多少个字节。
    • 例如，如果要发送一个包含10个整数的数组，count 就是 10。

  3. MPI_Datatype datatype: 发送元素的数据类型

    • 这个参数告诉 MPI，buffer 指向的数据是什么类型的。这与 count 参数配合，MPI 就可以计算出总共需要发送多少字节的数据 (总字节数 = count * sizeof(datatype)）。
    • MPI 预定义了很多类型，如 MPI_INT (对应 C 的 int)、MPI_DOUBLE (对应 double)、MPI_CHAR 等。

# 消息信封 (The "Who" and "How")

  1. int recipient: 接收者 (Recipient)

    • 你要把消息发送给哪个进程。这里填写的是接收进程的秩 (Rank)。在 MPI 中，每个进程都有一个从 0 开始的唯一整数ID，这个ID就是它的秩。

  2. int tag: 消息标签 (Tag)

    • 一个整数，你可以用它来区分不同类型的消息。
    • 接收方在调用 MPI_Recv 时可以指定只接收特定标签的消息。这就像邮件的“主题”，可以帮助接收者对消息进行分类和过滤。

  3. MPI_Comm communicator: 通信域 (Communicator)

    • 指定这个发送操作发生在哪个进程组内。一个通信域定义了一组可以互相通信的进程。
    • 在大多数简单程序中，这个参数都是 MPI_COMM_WORLD，它代表了参与当前 MPI 程序的所有进程。

# 3.3 MPI_Send 的一个重要特性：阻塞 (Blocking)

MPI_Send 是一个阻塞式 (Blocking) 的发送操作。这意味着什么？

当你的程序调用 MPI_Send 时，程序会**暂停（阻塞）**在该行，直到 MPI 系统确认发送缓冲区 (buffer) 的内容可以被安全地修改为止。

这通常意味着以下两种情况之一：

  1. 数据已经被完全拷贝到了接收进程的内存中。
  2. 数据已经被拷贝到了一个由 MPI 管理的、安全的临时系统缓冲区中。

关键点：一旦 MPI_Send 函数返回，你就可以立刻重用或修改 buffer 指向的内存，而不用担心会破坏正在发送的数据。

与之对应的是非阻塞发送 MPI_Isend，它会立即返回，允许你的程序在数据发送的同时继续执行其他计算，但你需要稍后手动检查发送是否完成。

# 3.4 一个简单的例子

假设进程 0 要发送一个整数 42 给进程 1：

// 假设 mpi_rank 是当前进程的秩
if (mpi_rank == 0) {
    // ---- 这是发送方 (进程 0) 的代码 ----
    int number_to_send = 42;
    
    // 调用 MPI_Send
    MPI_Send(
        &number_to_send,   // buffer: 数据的地址
        1,                 // count: 发送 1 个元素
        MPI_INT,           // datatype: 元素类型是 int
        1,                 // recipient: 发给进程 1
        0,                 // tag: 使用标签 0
        MPI_COMM_WORLD     // communicator: 在全局通信域中
    );
} 
else if (mpi_rank == 1) {
    // ---- 这是接收方 (进程 1) 的代码 ----
    int received_number;
    MPI_Status status; // 用于接收状态信息
    
    // 调用对应的 MPI_Recv
    MPI_Recv(
        &received_number,  // buffer: 存放接收数据的地址
        1,                 // count: 最多接收 1 个元素
        MPI_INT,           // datatype: 期望接收 int 类型
        0,                 // source: 从进程 0 接收
        0,                 // tag: 只接收标签为 0 的消息
        MPI_COMM_WORLD,    // communicator
        &status            // status: 接收状态
    );
    // 此时 received_number 的值会是 42
}

这个例子展示了 MPI_Send 如何与 MPI_Recv 配对使用，完成一次完整的点对点通信。
